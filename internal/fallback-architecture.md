# 各システムの想定機能一覧（内部検討用）

社外提出はしない、Orbit内部の設計検討メモ。ツチヤ自動車様への提案書（index.html）には反映していない。

粒度は「オートバックスアプリ見積り 08-13.pdf」のページリスト（大項目→画面→要件）に合わせている。基幹系連携の有無で内容・必要性が変わる画面には注記する。連携なしのパターン①②は[前提](#前提連携なしの2パターン)を参照。

## アーキテクチャ全体像：基幹系2という捉え方

```
[既存の基幹系]  ⇆ ①  ⇆  [基幹系2＝Orbitが新規構築するバックエンド]  ⇆ ②  ⇆  [①アプリ／②③④管理画面]
  （エンドが既に持っている）        （顧客・車両・予約・案件・フォロー・評価等を集約）      （スタッフ・営業・顧客が直接触る画面）
```

① 基幹系との連携部分：連携方式（API/CSV/連携不可）は明日以降のヒアリングで確定。**この文書のスコープでは扱わない**。
② 基幹系2とアプリ・管理画面の間のAPI：**ここが今回整理する範囲**。

ポイントは、エンドユーザー・店舗スタッフ・営業スタッフの操作は常に基幹系2に対して行われ、基幹系2が（連携できるなら）バックグラウンドで基幹系と同期する、という構造にすること。この形にしておけば、基幹系との連携方式がどう決まっても（API可／CSVのみ／連携不可）、アプリ・管理画面側のAPIはまったく変わらない。基幹系連携の結果に関わらず先に着手できる部分と言える。

## 基幹系2は1システムで良いか

①②③④が触るデータドメインを並べると、以下の4つに整理できる。

| データドメイン | 主に使うシステム | 参照するシステム |
|---|---|---|
| 会員・車両・予約 | ① | ②（顧客照合）、③（顧客・車両情報） |
| 反響・案件 | ② | ④A（CRM画面から参照。独自の案件データは持たない） |
| フォロー履歴 | ③ | ④A（担当営業の活動履歴として参照する可能性） |
| ロープレ・評価・スタッフ | ④A／④B | ③（担当営業の紐付け先） |

いずれも「顧客」「車両」「案件」という共通の主語でつながっており、矛盾なく1つのデータベース・1つのバックエンド（基幹系2）に統合できる。①アプリ、②③④の管理画面は別々のUIとして分かれていて良いが、その裏側のAPI・データストアは1つでよい（＝「別の資料として一旦考えようか」で話した通り、見せ方は4システム、実装は1つの基幹系2＋複数のフロントエンド）。

## 抜けている機能（不備）

当初のシステム別一覧に無かったが、レビューの結果追加した機能。各システムの表にも反映済み。

1. **②反響集約：未対応のSLA監視・エスカレーション通知**（提案書が掲げる「対応スピード↑」を実現する上で必須）
2. **②→③の橋渡し**（成約案件の顧客・車両・次回車検予定を③に自動登録。連携なしの場合、これが無いと③に新規客のデータが永久に入らない）
3. **①の予約実績と③のリマインドの整合**（既に予約済みの顧客への重複リマインドを防ぐ）
4. **④Bの評価サイクル・スケジュール管理**（評価基準はあっても、いつ実施するかの管理が無かった）

## 統合を検討すべき重複

- **②の対応履歴管理と④Aの商談・案件管理**：どちらも「案件が今どこまで進んでいるか」を追う機能。④Aは独自の案件マスタを持たず、②のデータを参照するビュー＋ロープレ機能の追加、という位置付けに整理（[基幹系2のAPI一覧](#基幹系2のapi一覧アプリ管理画面が呼ぶもの)にも反映済み）。
- 一方、①のマイページ（顧客本人が見る会員情報）と③の顧客詳細（スタッフが見る顧客情報）は、同じ顧客データの別の見え方であり重複ではない。共通データ基盤（基幹系2）を複数のUIから見る、という正しい形。

## 前提：「連携なし」の2パターン

- **パターン①：リアルタイム連携だけ不可**（初回一括移行は可能）
  基幹系から会員・車両データを最初に1回だけCSV等でもらい、以後はOrbit側が主として更新していく。
- **パターン②：完全に連携不可**（初回移行すらできない）
  既存データはゼロから作り直し・手入力。かなり稀なケースだが念のため想定。

どちらになるかで初期データ移行の工数が大きく変わる。ヒアリングメモ（打ち合わせ用トラッカー）にも「一括移行だけは可能か」を追加済み。

## 全体への影響（最重要）

[アーキテクチャ全体像](#アーキテクチャ全体像基幹系2という捉え方)で基幹系2を最初から1つの共通バックエンドとして設計する前提に立つと、「連携不可」の影響は当初想定していたより小さくなる。①②③が別々に会員・車両マスタを重複して持つ心配は無く、基幹系2という**既存の1つのシステムの中に、会員・車両等のマスタ機能を（基幹系から同期する代わりに）自前で持たせる**だけの話になる。

→ 「連携不可」は5つ目のシステムを新規に作る規模ではなく、**基幹系2内のデータ所有範囲が広がる**という規模で説明できる。ただし工数は増える（同期処理の代わりにマスタ管理UI・初期移行機能が必要になるため）。見積りへの影響はこの規模感で説明する。
